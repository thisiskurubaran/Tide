# Contributing to Tide

Thanks for helping. Bug reports, fixes, features and docs are all welcome.

By contributing, you agree that your contributions are licensed under the [MIT License](LICENSE), the same as the rest of the project. Please follow the [Code of Conduct](CODE_OF_CONDUCT.md). To report a security problem, see [SECURITY.md](SECURITY.md) instead of opening an issue.

## Reporting a bug

Open an issue with:

- the Tide version (shown next to What's new in Settings) and your device and iOS, iPadOS or Android version
- what you did, what you expected and what happened
- a screenshot or the error text, if you have them

Settings › Report a problem drafts an email with your device details and recent logs. Use it instead if you'd rather not post those publicly.

Check the open issues first; a 👍 on an existing one helps more than a duplicate.

## Suggesting a feature

Open an issue that describes the problem you're trying to solve, not only the feature. For anything large (a new runtime, a new panel, changes to Remote mode's sync protocol), agree on the approach in the issue before writing code.

## Setting up

The [README](README.md#getting-started) covers requirements and setup. In short:

```bash
cd app
npm install
npm run ios       # or: npm run android
```

Tide uses native modules, so Expo Go can't run it; use a development build. `app/ios` and `app/android` are generated by `npx expo prebuild` and are never committed. Change native setup through `app/app.json` or a config plugin in `app/plugins/`, not by editing the generated projects.

## Making a change

1. Fork the repository and create a branch from `main`.
2. Keep the change focused: one fix or feature per pull request.
3. Add or update tests next to the code you change (`*.test.ts` or `*.test.tsx`).
4. Run the checks for the parts you touched (below).
5. If the change is visible to users, add a line to the newest release in [`app/src/features/support/changelog.ts`](app/src/features/support/changelog.ts), then run `npm run build:changelog` from `app/` to update [CHANGELOG.md](CHANGELOG.md).
6. Open a pull request against `main`.

### Checks

| Area | Command |
|---|---|
| App tests | `cd app && npm test` |
| Type check | `cd app && npx tsc --noEmit -p .` |
| Server | `cd server && npm run typecheck && npm test` |
| Python runtime | `cd app/modules/python-runtime && python3 -m unittest discover -s tests` |
| Ruby/PHP runtime page | `cd app && npm run test:runtimes` |

The server's integration tests need Docker. The full list, including the Maestro end-to-end flows, is in the [README](README.md#testing).

### Generated files

Some third-party libraries are bundled into committed files (the editor and terminal WebViews, the git, SSH, database and Lua bundles). If you upgrade one of those libraries, run the matching `npm run build:*` command from `app/` and commit the output. See [Generated bundles](README.md#generated-bundles).

### Native code

Swift and Kotlin live in `app/modules/` (Expo modules), `app/native/` and `app/targets/` (widgets and Live Activities). Build on a device or simulator before opening a pull request; say in the pull request what you tested on.

## Commit messages

Write a short subject in the imperative ("Fix tab order after closing a pinned tab"), under about 70 characters, with no trailing period. Add a body when the reason isn't obvious from the diff: what was wrong, why this fixes it, and anything a reviewer should check. Keep unrelated changes in separate commits.

## Pull requests

Describe what changed and why, link the issue, and include screenshots or a short recording for UI changes. Expect review comments; small follow-up commits are fine and get squashed on merge if needed.
